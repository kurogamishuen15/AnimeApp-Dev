# F2.2 — Informe de correcciones de auditoría v2

## Estado actualizado — 2026-11-10, aceptación del propietario

Este addendum es el corte vigente y reemplaza las conclusiones de ejecución del
2026-11-09 cuando describen la suite/build como actuales. Se corrigió la causa
confirmada de controles duplicados: `media_kit_video_surface.dart` pasa
`NoVideoControls` al widget `Video`, con el tipo `VideoControlsBuilder?` de la
versión 2.0.1 instalada. En esa versión el sentinel es `null`, y `VideoState`
solo construye el overlay de controles si el callback no es nulo. Ahora existe
un único botón Play/Pause sincronizado con el snapshot y el tiempo se muestra
en formato legible. La revisión independiente detectó que un seek coalescido
podía quedar después de Stop. La página ahora descarta ese destino, rechaza
nuevos cambios del slider, espera que termine el seek activo y después ordena
Stop; el test nuevo comprueba `seek → stop` con un fake. No afirma cancelar una
operación nativa.

## Revalidación posterior — Flutter 3.47.9

El 2026-11-10 se preparó una segunda toolchain aislada en
`.ai-local/toolchains/flutter-3.47.9` (Flutter 3.47.9 stable, Dart 3.13.7),
compatible con el límite Dart del proyecto. Con `PUB_CACHE` local,
`flutter pub get --offline --enforce-lockfile` terminó con exit 0 y respetó el
lockfile.
También pasaron el widget test nuevo (2/2), los 32 tests player con libmpv real,
los 94 tests Flutter y el build Linux release seleccionando explícitamente
`lib/main_player_spike.dart`. Los ocho avisos informativos de `dart analyze`
no impidieron el exit 0. Flutter analyze en esa stable sigue fallando antes del
análisis por el defecto del canal LSP UTF-8 en la ruta Unicode del proyecto;
la beta 3.50.0-0.4.pre, por su parte, conserva el problema framework/engine
`SemanticsRole.slider`. Estos resultados no aportan evidencia gráfica ni
verifican el cierre GTK.

La corrida completa `bash scripts/ci.sh` terminó con exit 1 únicamente por
`flutter analyze` (exit 255, fallo LSP UTF-8); sus 40 pruebas Python, checker,
formato, análisis Dart, dependencias, suite Flutter de 94 pruebas y límites de
imports pasaron. No se declara CI verde con la stable disponible.

El cierre conserva el watchdog Dart de 15 s. Se añadió otro watchdog GTK nominal
de 20 s para un MethodChannel que no conteste: invalida esa generación, conserva
la ventana e ignora una respuesta tardía. Mientras la invocación original siga
sin callback, gestos posteriores no duplican la llamada; tras el callback, otro
gesto puede reintentar. Si no hay callback nunca, la ventana permanece abierta.
No se cancela cleanup ni se cierra por timeout. El archivo C++ del runner
compiló aisladamente con los flags del target generado; no hubo una ventana GTK
válida para probar el callback.

El primer intento del corte usó Flutter beta 3.50.0-0.4.pre/Dart
3.14.0-315.3.beta: analyze pasó, pero tests/build fallaron antes de la app
porque su framework no cubre `SemanticsRole.slider` declarado por `dart:ui`.
Los resultados de 87 tests/build del corte 2026-11-09 son históricos. La
revalidación estable descrita arriba sustituye el estado de tests/build para
este informe; el fallo de Flutter analyze stable se debe a otra limitación,
el protocolo LSP UTF-8 bajo la ruta Unicode.

Se intentó Broadway usando runtime/socket bajo `.ai-local/f2.2/`. GTK no pudo
crear EGL/OpenGL, Flutter no pudo crear platform view y media_kit pasó a
software rendering. Se observó un texture ID, pero no primer frame ni píxeles
visibles. La app y el daemon aislados terminaron con Ctrl-C/exit 130, no por
cierre GTK. No se usó la sesión gráfica principal. El propietario confirmó
audio/video en una ejecución anterior, previa a estas correcciones; no se
midió rendimiento actual. La auditoría independiente del 2026-11-10 está en
[`F2.2-audit-2026-11-10.md`](../ai-system/audits/F2.2-audit-2026-11-10.md).

## Resumen de cambios

- El slider mantiene el valor local durante el drag y llama a seek al terminar. Mientras hay un seek nativo en curso se conserva, como máximo, el destino pendiente más reciente.
- El cierre de ventana GTK para el entrypoint opt-in se coordina con Dart. La ventana solo se destruye tras el Future real de cleanup. No hay timeout que se interprete como cancelación nativa.
- El adaptador vuelve a validar `file:` y exige un archivo regular existente antes de llamar a `Player.open`.
- El fixture sintético puede generarse reproduciblemente con FFmpeg. El launcher determina la raíz por su propia ubicación y pasa esa raíz al entrypoint; este deriva el fixture fijo bajo `.ai-local/`. El helper de pruebas invoca el mismo generador cuando el fixture no existe y solo acepta una raíz validada.
- El launcher y el helper verifican que `.ai-local/`, `.ai-local/f2.2/` y `fixtures/` sean directorios reales, no symlinks, antes de generar o consumir el video.
- La superficie separa inicialización del controller, registro de textura por ID no nulo y primer frame procesado por el plugin. Las pruebas verifican que esos estados no se confundan.
- La integración real prueba stop→reopen, archivo inexistente, medio inválido, recuperación, avance, pausa, seek, stop y dispose. Fakes prueban inicialización fallida, cola de cierre y error de cleanup.
- Los README, ADR-002, ARCHITECTURE, ROADMAP, PROGRESS y TESTING reflejan las responsabilidades actuales y distinguen textura, primer frame del plugin y visibilidad del compositor.

## Fuentes oficiales consultadas (2026-11-09)

- [API `Player` de media_kit 1.2.6](https://pub.dev/documentation/media_kit/1.2.6/media_kit/Player-class.html): `open`, `stop`, `dispose` son Futures; `stop` descarga el medio y deja reutilizable Player. No establece que timeout de Dart cancele una operación nativa ni que dispose parcial sea reintentable.
- [API `VideoController` de media_kit_video 2.0.1](https://pub.dev/documentation/media_kit_video/2.0.1/media_kit_video/VideoController-class.html): expone `platform`, ID de textura y `waitUntilFirstFrameRendered`. Esta última representa el frame procesado/renderizado por el plugin; no certifica lo que presentó el compositor del escritorio.
- [Guía upstream actual de media_kit](https://github.com/media-kit/media-kit/blob/main/README.md) y [source upstream de VideoController](https://github.com/media-kit/media-kit/blob/main/media_kit_video/lib/src/video_controller/video_controller.dart), consultados mediante Context7 el 2026-11-09. Se contrastaron con las versiones bloqueadas y el source local de `media_kit 1.2.6` / `media_kit_video 2.0.1`; la guía `main` no sustituye el contrato de esas versiones fijadas.
- [Changelog de media_kit_video](https://pub.dev/packages/media_kit_video/changelog): documenta el retiro de `VideoController.dispose()` y el ciclo con Player/release. El código local resuelto se inspeccionó en pub cache versionado.
- [Flutter `Slider.onChangeEnd`](https://api.flutter.dev/flutter/material/Slider/onChangeEnd.html): callback al terminar una selección/drag; `onChanged` actualiza el valor durante la selección.
- [Flutter `State.dispose`](https://api.flutter.dev/flutter/widgets/State/dispose.html): método síncrono terminal; Flutter advierte que no se invoca necesariamente al cerrar la aplicación. Por eso el cleanup espera antes de destruir la ventana y el override solo elimina su suscripción/callback.

## Addendum de verificación focalizada — 2026-11-10

El propietario confirmó manualmente video visible con fotogramas cambiantes,
audio, una única interfaz de controles sin overlay adaptativo, Play/Pause y

Se backporteó en el SDK local aislado Flutter 3.47.9 el cambio upstream del

## Addendum — recuperación Stop → Play — 2026-11-10

El propietario reportó que Stop dejaba la salida gris y Play no retomaba. La regresión se reprodujo con libmpv real: en `media_kit 1.2.6`, Stop descarga la Media/playlist y el Player sigue vivo, pero un `play()` posterior no tiene elemento que reanudar. El adaptador ahora conserva la URI de la última apertura exitosa y el snapshot distingue `stopped` de Pause. Play tras Stop revalida el archivo y vuelve a abrirlo con autoplay en el mismo Player y VideoController; Play tras Pause solo reanuda. Stop sigue sin cerrar el motor. La UI muestra `Playback stopped · press Play to restart` sobre la misma superficie. Si el archivo desaparece, Play falla antes de invocar el motor y mantiene el estado para reintento.

La integración con libmpv ejecutada en este corte prueba Pause→Play preservando posición; dos ciclos Stop→Stop→Play sobre el mismo fixture, con estado detenido/posición cero, posición de inicio bajo un segundo y avance; y fuente local retirada/restaurada, con error observable y recuperación. El grupo focalizado de integración, snapshot y widget finalizó 14/14 con Flutter 3.47.9. Estos resultados prueban comandos/estado nativos y la UI en widget tests, pero no la textura ni los píxeles del compositor. La [issue upstream #957](https://github.com/media-kit/media-kit/issues/957) sigue abierta y describe negro en Linux tras Stop y reapertura de la misma URI. La verificación posterior del propietario confirmó visualmente Stop→Play en Fedora, incluidos imagen/audio y cierre normal GTK/proceso. No existe test automatizado completo del lifecycle nativo de VideoController. Informe focalizado: [`F2.2-stop-play-audit-2026-11-10.md`](../ai-system/audits/F2.2-stop-play-audit-2026-11-10.md). La verificación completa de esta intervención terminó con `bash scripts/ci.sh` exit 0: 40 pruebas Python de infraestructura, Flutter analyze/Dart analyze/formato/checker de imports y 99 pruebas Flutter. El build del target `lib/main_player_spike.dart` terminó exit 0. Logs conservados bajo `.ai-local/f2.2/evidence/stop-play-ci-final-2026-11-10.log` y `stop-play-linux-build-2026-11-10.log`. Focalizada final: 14/14. La auditoría de solo lectura independiente confirmó el gap visual P1 y que la prueba nativa no era explícita sobre tiempo de arranque; la última corrección añadió límite <1 s, ya ejecutada en la focalizada.
