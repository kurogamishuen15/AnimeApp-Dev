# Informe de auditoría y pruebas reales F1.5–F1.12

Fecha: 2026-11-09
Alcance: núcleo local de AnimeApp, F1.5 a F1.12
Resultado: validaciones locales aprobadas con Flutter beta aislado; varias
validaciones externas o semánticas siguen bloqueadas/pendientes.

## Resumen ejecutivo

Se ejecutaron pruebas con SQLite real en archivos bajo `.ai-local/`, servidor
HTTP loopback, reinicio de la base y desconexión efectiva. Se añadió un flujo
integrado de ajustes → SQLite → AniList adapter contra loopback → caché →
cierre/reapertura → conexión rechazada → recuperación con otro servidor. Se
compiló Linux release y `scripts/ci.sh` terminó con código 0.

La ejecución usó Flutter `3.50.0-0.4.pre` / Dart `3.14.0-315.3.beta` desde
`.ai-local/toolchains/flutter`. El canal aparece como `[user-branch]`; el SDK es
un checkout aislado de un tag de Flutter, no el SDK global. La suite completa
ejecutó 44 pruebas Flutter y CI ejecutó 40 pruebas de infraestructura IA. No se
llamó a AniList público, no se accedió al keyring del usuario y no se usaron
credenciales reales.

## Convenciones y entorno

- **U (unitario):** lógica aislada/fakes manuales. No sustituye validaciones de
  I/O externo.
- **I (integración local):** SQLite real en disco, HTTP solo loopback, proceso
  local y adaptadores reales.
- **E (externo):** servicio público, keyring real, OAuth real o backend remoto.
- Entorno observado: Fedora Linux 44, destino Linux x64. El SDK Android no está
  instalado; no se inicializaron Android, TV ni Windows.
- Las pruebas de base crean archivos en `.ai-local/test-db/`, verifican la
  raíz antes de limpiar y cierran/reabren las conexiones.
- Registros detallados de comandos, sin secretos ni credenciales:
  `.ai-local/validation/2026-11-09-f1_5_f1_12/final/` (no versionado).

## Defectos corregidos

1. **Notificaciones redundantes en SettingsStore.watch.** Se añadió una prueba
   que observó una emisión causada por escribir otra clave. Ahora el stream
   conserva y compara el JSON tipado validado y notifica solo cuando cambia el
   valor observable. También se verifica una escritura equivalente sin evento
   extra y una escritura distinta con evento.
2. **Reenvío de POST tras redirección.** El cliente AniList ahora establece
   `followRedirects: false`. Un fixture 307 loopback confirma que el segundo
   servidor no recibe el cuerpo de búsqueda y que el cliente devuelve error de
   red.
3. **HTTP 401 sin error de autenticación tipado.** HTTP 401 y errores GraphQL
   401 en HTTP 200 ahora mapean a `AuthAppError`; respuestas 400/403/5xx tienen
   resultados tipados probados.
4. **URL malformada podía interrumpir sanitización.** El logger sustituye una
   URL que no puede parsear por `[INVALID URL]`, y la prueba confirma que el
   evento se registra sin propagar `FormatException`.

## Revisiones independientes

- QA revisó los gaps previos de F1.5–F1.12 y confirmó la necesidad de aislar
  claves, comprobar desconexión real y distinguir fallbacks HTTP 503 de pérdida
  de transporte.
- Seguridad revisó sin acceder a red/keyring/cuentas. Confirmó ausencia de
  autenticación en cliente AniList y señaló la política de redirect y la
  sanitización de URL malformadas; ambas se probaron y corrigieron. No se
  observaron credenciales reales.
- Auditoría de código encontró además 401 sin `AuthAppError`, ausencia de TTL y
  límites del test de migración v1. El mapeo 401 se corrigió; TTL no se inventó
  y el alcance encadenado v1→v3 se describe con precisión.
- Auditoría de arquitectura confirmó que dominio sigue Dart puro, la
  composición de producto no integra los módulos todavía y F1.9–F1.11 siguen
  parciales. Se actualizó el README de app para evitar afirmar que esos módulos
  no existen.
- Revisión de seguridad final no encontró un defecto nuevo en redirect, 401 o
  URL malformada; confirmó cobertura en loopback/tests. Señaló como riesgo de
  producto decidir retención/borrado de consultas locales, separado de
  credenciales.

Las auditorías de seguridad, código y arquitectura son revisión estática; no
sustituyen las pruebas ejecutadas por el coordinador.

## Política de AniList y pruebas externas

La guía oficial de [términos de uso](https://docs.anilist.co/guide/terms-of-use)
restringe uso como sistema de respaldo/almacenamiento y servicios competidores
de listas o trackers. Como AnimeApp incluye catálogo/progreso de anime y no
existe confirmación de elegibilidad, la misión condiciona cualquier request a
la revisión previa. Por eso el conteo externo es **0**; la conectividad general
del host no se usó como sustituto de esa condición.

La documentación oficial describe el rate limit nominal de 90/min y el límite
degradado de 30/min en [rate limiting](https://docs.anilist.co/guide/rate-limiting).
La prueba de reloj simulado cubre ambos sin llamar a AniList.
