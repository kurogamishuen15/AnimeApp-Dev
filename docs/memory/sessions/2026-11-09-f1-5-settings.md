# F1.5 — Registro y store tipado de ajustes

Fuente: implementación y pruebas locales en `app/`
Fecha: 2026-11-09
Módulo: settings/registry y settings/store
Estado: infraestructura completada; catálogo concreto no aprobado
Commit: `5a7bab2`
Decisión: no inventar claves, defaults o alcance de sincronización ausentes de los documentos
Evidencia: READMEs del módulo, pruebas de integración y CI completa

## Implementación

- `SettingDefinition<T>` declara clave, propietario, valor por defecto, codec JSON y validador tipado. Rechaza metadata vacía y default inválido.
- `SettingsRegistry` valida unicidad y resolución por identidad/tipo.
- `SettingsStore` usa Drift local-first con `get`, `set` y `watch`; defaults aplican sin fila, cambios se escriben a SQLite y el stream observa actualizaciones. Errores se expresan con `Result<T>` y tipos de F1.7, incluidos fallos de la fuente del stream.
- Secretos quedan excluidos. No se registran definiciones de producto: ADR-A06 dice explícitamente que el plan no enumera preferencias, defaults o sensibilidad.
- Los tests usan solo una clave sintética `test.counter`; no representa una preferencia aprobada.

## Verificación

- `dart analyze lib/settings test/settings`: sin issues.

- `python3 tools/ai/memory.py check`: sin conflictos.

## Pendiente de definición

El propietario aún debe aprobar por cada preferencia concreta su nombre estable, tipo, default y alcance de sincronización antes de registrarla. Eso no impide cerrar y verificar la infraestructura genérica; no se persisten opciones sin definición aprobada.
