## Resumen ejecutivo

Se confirmó el defecto de dos barras: el `Video` usado por `MediaKitVideoSurface` omitía `controls`, cuyo default en `media_kit_video 2.0.1` es `AdaptiveVideoControls`. En Linux, ese builder monta los controles de escritorio, además de la barra de `SpikePlayerPage`. La superficie ahora pasa `NoVideoControls` tipado como `VideoControlsBuilder?`; con la versión bloqueada, el sentinel es `null` y el propio `VideoState.build` omite por completo el subtree de controles. La página tiene un solo control Play/Pause sincronizado con el snapshot, Stop y slider con tiempo legible. Se añadió prueba de regresión sobre la propiedad efectiva usada por producción.

El cierre ahora tiene un watchdog de respuesta de 15 segundos. Al vencer, retorna `false` a GTK para conservar la ventana, presenta un aviso y mantiene el mismo Future de cleanup; no cancela la operación nativa ni solicita un segundo dispose mientras continúa el primero. Un probe Dart independiente pasó esa política y el guard de symlinks del launcher/generador quedó cubierto por prueba shell.

La revisión independiente encontró dos defectos adicionales: un destino de seek coalescido podía ejecutarse después de Stop, y GTK podía dejar el cierre pendiente indefinidamente si el MethodChannel no respondía. La UI ahora descarta el destino todavía no iniciado, espera el seek activo y luego envía Stop; GTK tiene un watchdog nativo nominal de 20 segundos que quita el guard local e invalida una respuesta tardía. Solo se permite una invocación MethodChannel pendiente: una nueva llamada puede salir después de que llegue el callback antiguo; si nunca llega, la ventana sigue abierta sin duplicar solicitudes. Ninguno de esos watchdogs cancela cleanup nativo. Se añadió una regresión que exige `seek, stop` y el objeto C++ modificado se compiló directamente.

La toolchain beta 3.50.0-0.4.pre/Dart 3.14.0-315.3.beta pasa Flutter analyze, pero sus tests/build no arrancan: `dart:ui` incluye `SemanticsRole.slider` y su framework no cubre el valor en `semantics.dart:164`. Para validar sin cambiar dependencias se preparó dentro de `.ai-local/toolchains/` Flutter estable 3.47.9/Dart 3.13.7, cuya restricción satisface `pubspec.yaml`; con ella pasaron el test nuevo de startup/cierre, los 32 tests player, los 94 tests Flutter y el build Linux release con el entrypoint del spike explícito. `flutter analyze` en esa stable aún falla antes de analizar la app por el defecto LSP UTF-8 ya registrado en TESTING.md; `dart analyze` termina 0 con ocho sugerencias informativas existentes. Así quedan cubiertos los tests y build requeridos, pero no la validación visual ni el cierre real GTK. Un intento gráfico aislado con Broadway tampoco produjo una superficie visible: Flutter informó backend sin EGL/OpenGL y no creó platform view. No se usó ni controló el escritorio principal. Los 87 tests/build del 2026-11-09 siguen siendo históricos, sustituidos para la comprobación actual por la corrida estable 3.47.9.

## Cierre GTK y propiedad de recursos

`SpikePlayerModule.open` crea un solo `MediaKitSpikeEngine`, un solo `Player` y un `VideoController` enlazado a ese Player. La UI recibe el mismo controller y no importa Player. `SpikePlayerCoordinator` serializa comandos y dispose; el lease permanece ocupado hasta completar cleanup. El callback GTK `delete-event` en [`my_application.cc`](../../../app/linux/runner/my_application.cc) existe solo cuando `KONGROO_F2_2_SPIKE=1`, retorna `TRUE` y evita destrucción inmediata. GTK destruye la ventana si Dart responde `true` tras el cierre del módulo o tras liberar correctamente los recursos del rollback de una apertura fallida; en caso de fallo de cleanup la ventana se conserva.

El watchdog añadido en [`spike_window_close_gate.dart`](../../../app/lib/app/player/spike_window_close_gate.dart) no se interpreta como cancelación (línea 3). Si el timeout gana la carrera, Dart responde `false` y GTK conserva la ventana; el Future de limpieza sigue observado en `_cleanup`. Una nueva petición comparte ese Future pendiente, y si más tarde finaliza con éxito una petición posterior puede cerrar. Si el dispose falla, el gate reintenta solo el cleanup que el adapter permite; la cuarentena del lease impide reemplazar un Player con estado nativo incierto.

El probe `dart tools/player/verify_f2_2_close_gate.dart` ejercita el gate Dart sin Flutter: dos solicitudes simultáneas se coalescen; el watchdog responde `false`; el Future de cleanup sigue incompleto; una segunda petición no inicia otro callback; al completar el cleanup, se permite el cierre. **No verifica** `delete-event`, el MethodChannel, destrucción GTK, salida del proceso ni VideoController nativo. El runner ahora añade un watchdog GLib de 20 s. Si GTK sigue procesando eventos pero el isolate/canal no responde, invalida esa generación y quita el guard local; no destruye ventana ni cancela cleanup. Mientras la invocación MethodChannel siga pendiente, los siguientes cierres se mantienen abiertos sin mandar solicitudes duplicadas. El callback usa una generación como `user_data` y obtiene la aplicación mediante `GWeakRef`, evitando acumular referencias fuertes por cada reintento. Si la única invocación nunca responde, esa tarea/canal puede seguir pendiente y la ventana permanece abierta; no se afirma una cancelación del transporte o de cleanup. GLib documenta que los timeouts usan tiempo monótono, se pueden retrasar por otras fuentes del main loop y tienen granularidad aproximada de segundos, así que no son un límite duro si el propio loop se bloquea. Ese último caso y la integración nativa siguen sin probarse.

La documentación oficial de Flutter indica que la integración desktop Linux normalmente requiere un servidor X (por ejemplo, Xvfb). En esta máquina no se encontraron `Xvfb`, `xvfb-run`, Weston, Cage, Xephyr ni gamescope; no se instalaron paquetes. Broadway está disponible, pero esta ejecución confirmó que el embedder/plugin de Flutter no presenta la superficie por ese backend.

El estado de video/audio visible confirmado por el propietario en una ejecución anterior se conserva como evidencia histórica. No se reutiliza como prueba de la UI corregida.

## Revisión independiente y cierre

Las revisiones adversariales `auditor_codigo` se realizaron secuencialmente y en solo lectura. La primera detectó el seek en cola que podía ocurrir tras Stop; la segunda confirmó estáticamente que el arreglo descarta el destino pendiente, espera el activo, bloquea nuevas entradas y comprueba el orden con un fake. También detectó el README general de app desactualizado y el cierre GTK pendiente ante canal sin respuesta. La tercera detectó que los callbacks podrían retener una ref fuerte de la app por cada gesto; se cambió a generación como `user_data`, `GWeakRef` y máximo una invocación MethodChannel sin callback. La cuarta confirmó que no se acumulan refs fuertes ni existe UAF en callbacks tardíos. La revisión final no encontró defectos P0–P2 en controles, seek/Stop ni ownership; encontró N9 y N10, que se corrigieron después. El límite explícito permanece: si el callback nunca vuelve, no se emiten nuevas llamadas y la ventana permanece abierta. Ninguna revisión ejecutó pruebas ni sustituye el runner Flutter/native bloqueado por N1 o el ciclo visual GTK de N2/N3.

**Recomendación al corte de auditoría: PENDIENTE.** Este corte precedió al backport local LSP, CI exit 0, build del entrypoint y verificación manual posterior del propietario. La recomendación de no aceptación queda supersedida por el addendum formal al final de este documento. La limitación vigente es la ausencia de test automatizado end-to-end del lifecycle nativo de VideoController; F2.3 no se inicia sin autorización.
